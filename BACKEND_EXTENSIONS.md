# Расширения бекенда — план после ревизии 25

B-1…B-8 закрыты, better-sqlite3 в Node-sidecar стал основным хранилищем.
Дальше бекенд растёт отсюда. Каждый этап — атомарный коммит с тестами,
ворота те же: cargo test/clippy 0, svelte-check 0/0, pnpm test, бандл в
бюджете, деплой + bench-out/startup.json, запись в DECISIONS.md.

Порядок — по соотношению «польза / риск». Начинаем с E-1: без него
остальное не доедет до чужой машины.

## E-1: Упаковка sidecar в бандл (обязательный следующий шаг)

Сейчас better-sqlite3 работает, потому что Node стоит на машине разработки.
На чужой машине приложения без Node упадёт в rusqlite-фолбэк — это тихо и
неправильно: пользователь просил better-sqlite3.

- Положить `node.exe` + `sidecar/` (скрипт и `node_modules/better-sqlite3`
  с бинарником) в tauri `resources`; `sidecar_script()` уже ищет рядом с exe.
- CI: шаг, который качает prebuilt better-sqlite3 под Node LTS и кладёт в
  артефакт (prebuild-install в pnpm-скрипте `sidecar`, с явным
  `--runtime node --target <версия>` — урок ревизии 25: окружение с
  ELECTRON_RUN_AS_NODE путает рантайм).
- Пиннинг версии Node в `.nvmrc`/доке: ABI бинарника (v137) обязан
  совпадать с.major рантайма.
- Критерий: `SWAGCOD_STORE=node` на чистой машине (без Node в PATH)
  поднимает базу; bench без регресса (старт < 400 мс).

## E-2: Семантический поиск по кодовой базе (embeddings)

Агент ищет код грепом; для «найди где обрабатывается оплата» нужен смысл.

- Таблица `embeddings(chunk_id, path, start, end, vec BLOB)` в той же базе
  better-sqlite3; чанки по ~40 строк с перекрытием.
- Индексация фоном при открытии сессии (watcher из B-4 уже знает об
  изменениях — переиндексация только тронутых файлов).
- Провайдер эмбеддингов — тот же Router (B-6): `/v1/embeddings`, фолбэки
  работают из коробки; кэш по хэшу содержимого, чтобы не платить дважды.
- Косинусный поиск brute-force до ~50k чанков (SQLite-скаляр хватит);
  дальше — hnsw-подобный индекс отдельным этапом.
- Инструмент `semantic_search` в реестре B-5 с обычной политикой
  подтверждений (чтение — безопасно).

## E-3: MCP-клиент (Model Context Protocol)

Внешние серверы инструментов — стандарт, который ждут от агента в 2026.

- stdio-транспорт: spawn процесса сервера, JSON-RPC 2.0, discover
  `tools/list`, вызов `tools/call` — по образцу плагинов B-5, но с
  MCP-схемой аргументов и таймаутами.
- Реестр MCP-серверов в настройках (prefs): команда, env, разрешения;
  каждый tool вызова идёт через ту же approval-машину (журнал B-7
  получает `actor`/`tool` с префиксом `mcp:`).
- Ресурсы и промпты MCP — второй очередью; сначала только tools.

## E-4: JS-плагины в sidecar (горячая загрузка)

Node теперь и так живёт рядом с приложением — грех не дать плагинам
быть обычным JS вместо отдельных exe (B-5).

- Каталог `plugins/*.js` грузится в sidecar-процесс (отдельный воркер или
  vm-контекст с таймаутом), манифест описывает инструменты.
- Те же гарантии, что у exe-плагинов: политика подтверждений, журнал,
  изоляция по времени (watchdog B-8 следит за ходом, а не за плагином —
  плагин обязан отвечать в дедлайн).
- Мост к хранилищу: плагины получают read-only API prefs (не сессий —
  приватность).

## E-5: Фоновые задачи и планировщик

- Таблица `tasks(id, kind, payload, state, attempts, next_try_ms)` +
  воркер в ядре: ретраи с backoff (механика B-6 переиспользуется),
  отмена, журнал прогонов.
- Первые потребители: переиндексация эмбеддингов (E-2), периодический
  `git fetch` для diff-панели, экспорт журнала.

## E-6: Суб-агенты и параллельные ходы

- Дерево ходов: `parent_turn_id` в turns, бюджет токенов на ветку,
  изолированная история (контекст B-3 копируется по желанию).
- UI: параллельные сессии уже живут (liveStates), добавить ветки в
  траектории.

## E-7: Локальный HTTP API / удалённое управление

- Только loopback, токен в DPAPI-хранилище (механика B-7).
