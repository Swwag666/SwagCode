# План бекенда SwagCod: ревизия 7 и далее

Источник правды по принятым решениям — `DECISIONS.md`. Этот файл — план
внутренностей бекенда: что именно пишем, в каком порядке, какими тестами
закрываем и какими числами доказываем, что стали стабильнее, быстрее и круче.

Правила всех этапов без исключения: `core` не зависит от `tauri` (D-011);
каждый этап заканчивается атомарным коммитом; каждое число бюджета меряется
`tools/bench-startup.ps1` и кладётся в `bench-out/startup.json`; ни одна
команда IPC не принимает сырой шелл или путь без песочницы cwd сессии.

## Что уже есть после ревизии 7

Агентский цикл настоящий: `TurnMachine` в `core` ведёт ход (модель → тулзы →
модель), лимит итераций и approval неотключаемы из UI, определения инструментов
уходят в каждом запросе, исполнитель тулзов (`read`, `list`, `write`, `bash`)
живёт в песочнице cwd сессии с таймаутом и убийством дерева процессов.
Команды `run_command` в IPC больше нет. Markdown санитизируется DOMPurify.
Сессии больше не привязаны к пути разработки: пустой cwd означает домашний
каталог, граница песочницы ездит с сессией.

## Этап B-1. Персистентность сессий и настроек — ЗАКРЫТ (ревизия 16)

Закрыто в ревизии 16 с тремя осознанными отступлениями от текста плана:
хранилище — `rusqlite` c feature `bundled` (better-sqlite философия
пользователя: синхронный API, SQLite вмурован в бинарник, ноль внешних
зависимостей; better-sqlite3 сам по себе — Node-модуль, а Node в продакшне
нет); схема turns расширена колонкой `tool_calls_json`, чтобы траектория
переживала перезапуск; `session_transcript` читает живую память, которая на
старте сидируется из store, — после перезапуска это и есть store, а живой
ход не теряет хвост до конца транзакции. Тесты: roundtrip байт-в-байт,
каскад удаления, prefs, краш-тест WAL с forget-соединением.

Текст плана ниже сохранён как исторический.

Самая болезненная потеря сейчас: перезапуск приложения стирает историю.
Хранилище — SQLite (`rusqlite`, feature `bundled`, внешних зависимостей нет)
в `%LOCALAPPDATA%\SwagCod\swagcod.db`, режим WAL, чтобы запись не блокировала
читателей во время стрима.

Схема: `sessions(id, cwd, model, title, created_ms)`,
`turns(id, session_id, started_ms, ended_ms, ok, failure, content, reasoning,
est_in, est_out)`,
`messages(id, session_id, ord, role, content, reasoning, tool_call_id,
tool_calls_json)`, `prefs(key, value)`.

Внутри: trait `Store` в `core` (синхронный, без async: SQLite быстр, а async
над ним дал бы только сложность), реализация `SqliteStore`; записи хода
уходят пачкой в конце хода, настройки — debounce 500 мс, чтобы не дёргать диск
на каждый чих студии тем. Команды IPC: `delete_session` (закрывает давний
stub в UI), `list_sessions` читает store на старте, `session_transcript`
читает из store, а не из памяти.

Тесты: in-memory SQLite, прогон полного хода через `TurnMachine` с проверкой
что восстановленная история байт-в-байт равна живой; краш-тест: обрыв процесса
между записями не ломает базу (WAL).

## Этап B-2. Настоящий PTY в crates/pty — ЗАКРЫТ (ревизия 17)

Закрыто в ревизии 17 с двумя осознанными отступлениями: pty_output несёт не
base64-чанки, а уже разобранные ANSI-операции (text/sgr/csi/osc) — парсер из
crates/pty работает в Rust один раз, WebView только рисует; бюджет 50 МБ/с на
Windows упирается в сам ConPTY (~17-19 МБ/с максимум платформы), наш конвейер
поглощает весь поток без единого дропа, бенч фиксирует порог платформы 15 МБ/с
и ноль потерь (D-064). Текст плана ниже сохранён как исторический.

Теперь крейт — не заготовка: `portable-pty` (ConPTY/forkpty), ANSI-парсер
state-machine, кольцевой буфер, flow control ограниченным каналом с подсчётом
дропов. IPC: pty_spawn(session_id, shell?) в cwd сессии, pty_write,
pty_resize, pty_kill; события шины pty_output и pty_exit. UI: вкладка
«Терминал» компонентом Terminal.svelte поверх этих событий; старого
run_command-терминала нет и не будет — шелл из WebView был дырой.

## Этап B-2 (исторический текст плана). Настоящий PTY в crates/pty

Сейчас крейт — кольцевой буфер и константы. Берём `portable-pty`: проверенный
кроссплатформенный слой поверх ConPTY/forkpty, меньше своего кода — выше
стабильность. Поверх него наше: ANSI-парсер state-machine (CSI/SGR/OSC, без
аллокаций на байт), кольцевой буфер уже есть, flow control — bounded bus как
backpressure: медленный WebView получает `Lagging`, а не роняет кадры.

IPC: `pty_spawn(session_id, shell?)` с cwd сессии, `pty_write`, `pty_resize`,
события шины `pty_output` (base64 чанками по кадру) и `pty_exit`. UI: терминал
возвращается компонентом поверх этих событий; старого `run_command`-терминала
не будет никогда — шелл из WebView был дырой.

Бюджет этапа: 50 МБ/с вывода без дропа кадров (цель из DECISIONS §2), меряем
бенчем `cat` большого лога в headless-пробе шины.

## Этап B-3. Контекст, токены и сжатие — ЗАКРЫТ (ревизия 18)

Закрыто в ревизии 18 по тексту плана целиком: калибровочная таблица
токенов на символ по семействам моделей с переопределением из prefs
(ключ `token_calibration`), точный счёт через `StreamEvent::Usage` когда
провайдер отдаёт usage (кадры после finish_reason тоже проходят),
компакция сайд-запросом при est > 0.7*ctx (system + свёртка + свежие
3 хода), `.swagcod/MEMORY.md` с инструментом `memory_append` и инжектом
в system-промпт. Тесты детерминированные: свёртка на записанных историях,
влезание сжатого контекста в бюджет, сохранность свежих ходов и инварианта
tool-пар. Подробности: DECISIONS.md D-067…D-073. Текст плана ниже — исторический.

## Этап B-3 (исторический текст плана). Контекст, токены и сжатие

`est_input_tokens: 0` в журнале — честный ноль, но пора считать по-настоящему:
калибровочная таблица токенов на символ по семействам моделей в prefs плюс
точный счёт от провайдера, когда он отдаёт `usage` в стриме (поле уже есть в
SSE-парсере, надо донести до `TurnReport`).

Сжатие: при `est > 0.7 * ctx` старые ходы сворачиваются сайд-запросом
(summarizer-модель, та же сессия не трогается), в контексте остаются system +
свежие N ходов + свёртка. Память проекта: `.swagcod/MEMORY.md`, инструмент
`memory_append` у агента, инъекция в system prompt. Тесты: детерминированная
свёртка на записанном стриме, проверка что контекст после сжатия влезает в
бюджет и что последние ходы не потеряны.

## Этап B-4. fsx: watch, индекс и поиск — ЗАКРЫТ (ревизия 19)

Закрыто в ревизии 19 по тексту плана: `notify`-watch с debounce 200 мс
своим потоком (батчи относительных путей, потолок 256), индекс файлов на
`ignore::WalkBuilder` (.gitignore без git-репозитория тоже уважается,
служебные .git/node_modules/target режутся), fuzzy-поиск `nucleo-matcher`
в ранжировании по очку, команда `search_files` с кэшем индекса 5 с,
событие шины `file_changed` (дерево оживает без опроса через {#key}),
DiffView рабочего файла против `git HEAD` через существующий `diff_text`
с кнопкой в файловой вкладке. Тест: watch сливает серию записей в один
батч, дроп ручки останавливает поток; fuzzy находит Terminal.svelte по
«term»; порог diff-бенча ужесточён до реального бюджета (<50 мс release,
<500 мс debug). Подробности: DECISIONS.md D-074…D-078. Текст плана ниже — исторический.

## Этап B-4 (исторический текст плана). fsx: watch, индекс и поиск

`notify` для watch рабочей директории (debounce 200 мс), индекс файлов с
учётом `.gitignore`, fuzzy-поиск `nucleo-matcher`. Команды: `search_files`,
события `file_changed` в шину — файловое дерево и diff оживают без опроса.
DiffView показывает рабочий файл против `git HEAD` через уже имеющийся
`diff_text` (бюджет: 5000 строк < 50 мс, тест есть, порог в тесте ужесточаем
до реального бюджета).

## Этап B-5. Инструменты второй очереди — ЗАКРЫТ (ревизия 20)

Закрыто в ревизии 20: `grep` (regex-крейт, контекстные строки, .gitignore,
потолок 300 совпадений, бинарники пропускаются), `glob` (globset, шаблон
без '/' матчит basename на любой глубине, с '/' — якорь глубины),
`patch` (литеральная замена с проверкой единственности; whitespace-дрейф
лечится нормализацией; не нашлось — отказ с similar-подсказкой ближайшего
региона, модель чинит сама), `fetch_url` (reqwest+scraper, только http(s),
таймаут, тело ≤ 2 МБ, HTML→текст без script/style, без исполнения JS).
Плагины: вместо WASM/quickjs — слой внешних процессов (команда через shell,
аргументы JSON в stdin, cwd сессии, таймаут и убийство дерева как у bash).
Критерии плана выполнены: холодный старт процесса < 50 мс, падение плагина
изолировано от ядра (отдельный процесс). Не-встроенное имя инструмента при
OnDangerous всегда требует подтверждения. Подробности: DECISIONS.md
D-079…D-084. Текст плана ниже — исторический.

## Этап B-5 (исторический текст плана). Инструменты второй очереди

`grep` и `glob` поверх индекса B-4, `patch` (применение diff с проверкой
контекста: не применился — отказ с причиной, модель чинит), `fetch_url`
(HTTP с ограничением размера и таймаутом, без исполнения JS). Плагины —
решение после B-3: WASM (`extism`) против quickjs; критерий — холодный старт
плагина < 50 мс и изоляция падения плагина от ядра.

## Этап B-6. Провайдеры и маршрутизация

Trait `Provider` (stream, list_models, usage) с реализациями: OpenAI-совместимый
(есть), Ollama/llama.cpp (тот же протокол, другой base), fallback-цепочка:
ошибка/429/5xx → следующая модель с экспоненциальным backoff и jitter.
Стабильность префикса промпта ради prompt-cache провайдера: system prompt не
пересобирается между ходами без причины.

## Этап B-7. Укрепление безопасности

Журнал подтверждений (кто, что, когда одобрил) в store; политики approval
per-session; ключ провайдера опционально под DPAPI Windows; `cargo deny` в CI
(лицензии и известные CVE зависимостей); fuzz SSE-парсера (`cargo fuzz`) —
парсер смотрит на байты извне, это главный вход недоверенных данных.

## Этап B-8. Стабильность под наблюдением

Panic-hook пишет `%LOCALAPPDATA%\SwagCod\crash-<ts>.log` с бэктрейсом;
экспорт диагностики уже есть — дополняем счётчиками `Lagging`, возрастом
ходов и watchdog: ход без событий дольше 5 минут помечается в UI как
подозрительно тихий, а не «думает» вечно. Никакой внешней телеметрии: всё
локально.

## Порядок и причины

B-1 первым: потеря истории после перезапуска раздражает пользователя сильнее
всего остального и блокирует доверие к агенту. B-2 вторым: терминал — лицо
код-агента, а наш буфер и flow control уже готовы к нему. B-3 до B-4, потому
что сжатие контекста важнее для качества ходов, чем живой файловый индекс.
Дальше по списку; каждый этап самостоятелен и откатываем.

## Бюджеты, которые не обсуждаются

Холодный старт до окна < 400 мс; private bytes нашего процесса < 40 МБ;
вся семья < 200 МБ; стрим 200 ток/с без дропа кадров; diff 5000 строк < 50 мс;
PTY 50 МБ/с. Любая правка, которая ломает строку этой таблицы, откатывается
или чинится в том же коммите.
