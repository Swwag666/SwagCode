# VoidSearchSwag - план v3 (Go, self-hosted MCP)

**Идея:** автономный поисковый движок как MCP-сервер на Go. Мозг - любой подключённый LLM-клиент (Claude, другой агент, свой оркестратор). Сам сервис - чистый инструментарий: поиск, парсинг, классификация, onion-разведка. Встраивается в другие проекты как "умный поиск" одним подключением к MCP или импортом пакета.

**Почему Go (а не Python):**
- Сетевое ядро - вся нагрузка проекта: массовый параллельный probe прокси, краулинг, флуд запросов. Горутины дешевле asyncio-тасков на порядок.
- Существующий боевой стек в TeamSWAGbot (обкатан на kleinanzeigen с Akamai): proxypool, fingerprint, tor-rotator. Портируется почти без изменений.
- `bogdanfinn/tls-client` + `fhttp` - лучшая TLS-имперсонация (JA3/JA4 + HTTP/2 frames + порядок заголовков). В Python аналога нет, есть костыли.
- Один статический бинарь на выходе: отдал исполняемый файл - и всё работает. Никаких venv/pip/зависимостей.
- LLM на стороне клиента → главный аргумент за Python (ML-экосистема) исчез.

**Что вырезано из v1 и почему:**
- Telegram-бот → внешняя зависимость, UI не ядро. Результаты отдаются через MCP, клиент сам решит как показывать.
- VirusTotal → внешний ключ, квоты, узкое горлышко. Файлы не скачиваются вообще - агент отдаёт каталог ссылок с метаданными.
- Ollama/локальная LLM → слабый tool calling на 4B. LLM-интеллект живёт на стороне клиента MCP, сервер остаётся лёгким.
- Docker → MCP запускается локально, контейнер ради двух процессов - оверкилл. Tor живёт как дочерний процесс приложения, весь стейт в `~/.voidsearchswag/`.

## Стек

| Слой | Решение | Откуда |
|---|---|---|
| MCP | `mark3labs/mcp-go` (stdio + SSE/streamable-http) | новое |
| HTTP + антидетект | `bogdanfinn/tls-client` + `fhttp` + `impersonate-http`: JA3/JA4 + H2-фреймы + порядок заголовков, 7 отпечатков | порт из TeamSWAGbot `fingerprint.go` |
| Браузер | `go-rod/rod` + `go-rod/stealth` (headless, когда HTTP не хватает) | уже в TeamSWAGbot go.mod |
| Tor | `nao1215/tornago`: дочерний демон, NEWNYM-ротация с cooldown | порт из TeamSWAGbot `identity.go` |
| Прокси | ProxyScrape API + статический пул, probe с двумя целями, LRU, персистентный state | порт из TeamSWAGbot `proxypool.go` |
| DOM-парсинг | `goquery` + `cascadia` (CSS), `golang.org/x/net/html` (скелет для LLM) | уже в TeamSWAGbot |
| БД | SQLite через `modernc.org/sqlite` (без CGO - бинарь остаётся статическим) | новое |
| Конфиг/логи | `caarlos0/env`, `zerolog` | как в TeamSWAGbot |

## Этап 0: Фундамент (1-2 дня)

**Цель:** база, на которой всё держится.

- Приватный репозиторий `VoidSearchSwag`, лицензия, .gitignore, `go.mod` (go 1.25).
- Портирование из TeamSWAGbot в `internal/netx/` (отвязать от kleinanzeigen):
  - `proxypool.go`, `poolstate.go`, `proxyurl.go` - как есть, Provider-интерфейс оставить
  - `fingerprint.go` - как есть
  - `identity.go` - Rotator (tor/proxy/pool/direct) как есть
- Tor как дочерний процесс через tornago: Expert Bundle скачивается на `setup` в `~/.voidsearchswag/vendor/tor/`.
- Схема SQLite сразу (это 2 часа сейчас или 2 дня боли потом):
  - `sources` - найденные источники (url, type, quality, first_seen, last_ok)
  - `onion_pool` - onion-сервисы (url, status, latency_avg, success_rate, last_probe, category)
  - `selectors` - селекторы парсеров (url_pattern, field, selector, strategy, confidence, updated_at)
  - `hunts` - фоновые мониторинги (query, mode, schedule, last_run, last_hash)
  - `cache` - кэш поисковых выдач (query_hash, mode, payload, ttl)
  - `tasks` - реестр фоновых задач (id, kind, status, progress, result_ref)
- `Makefile` (setup, test, run, build), README с идеей и архитектурой.

**Критерий готовности:** `voidsearchswag run` поднимает MCP-сервер и tor-демон, `--help` работает, миграции SQLite применяются, proxypool проходит юнит-тесты после порта.

## Этап 1: Поисковое ядро (3-4 дня)

**Цель:** искать в трёх режимах + авто-выбор режима. Референсы: OnionClaw, robin.

### 1.1. Fast-поиск (clearnet)

Цепочка фоллбэков, не один канал:
1. Brave Search API (2000 запросов/мес бесплатно, без капч)
2. DuckDuckGo lite/html (парсинг, стабильная вёрстка)
3. rod + stealth → Google (только когда первые два упали)

Модуль: `internal/searchers/clearnet.go`, единый интерфейс `Search(ctx, query) ([]Result, error)`.

### 1.2. Deep-поиск (Tor)

- Tor-демон через tornago (SOCKS5 на свободном порту).
- tls-client через `socks5://` транспорт: fingerprint работает и в onion-зоне.
- Асинхронный движок по onion-поисковикам (ядро из OnionClaw, переписанное на горутины): `internal/searchers/onion.go`.
- NEWNYM-ротация с cooldown (готовая логика из identity.go).

### 1.3. Health-pool onion-поисковиков

Критично: половина onion-поисковиков мертва в любой момент.
- Фоновый probe каждые N минут (горутина + таймаут).
- Скоринг: `success_rate`, `latency_avg`, авто-выключение при 3 подряд фейлах, авто-возврат при успешном probe.
- Поиск идёт только по живым, в порядке приоритета по скору.

### 1.4. Авто-выбор режима

`internal/router/mode.go`:
- Быстрые эвристики: слова "утечка/onion/даркнет/paste" → deep; "новости/быстро" → fast; домен с известной антибот-защитой → stealth.
- Результат: `{mode, reason, fallback}` - детерминированно, без LLM.
- LLM-клиент может переопределить: режим - явный параметр каждого MCP-инструмента, `auto` по умолчанию.

### 1.5. Кэш

SQLite TTL-кэш (по умолчанию 1 час), ключ = hash(query + mode).

**Критерий готовности:** `search("site:pastebin.com password", mode="auto")` возвращает ссылки; при убитом вручную поисковике выдача не деградирует (health-pool переключил на живых).

## Этап 2: Onion-разведчик (2-3 дня)

**Цель:** агент САМ находит onion-источники, пул не зашит в код.

### 2.1. Сидовые каталоги

`internal/discovery/seeds.go` - парсинг живых индексов:
- Ahmia.fi (clearnet-фронт, не надо жечь Tor)
- dark.fail, onion.live (верифицированные списки)
- Hidden Wiki зеркала
- Найденные поисковики (Tordex, Tor66 и др.)

### 2.2. Краулер-валидатор

`internal/discovery/crawler.go`:
- Из каждой страницы выдёргивает `.onion` ссылки (regex + goquery по href).
- Probe: доступность, таймаут, код ответа - массовый параллелизм на горутинах (аналог FilterLive).
- Классификация грубая по контенту: search engine / forum / market / paste / wiki / other.
- Всё живое → `onion_pool` с категорией.

### 2.3. Саморасширение

Рекурсивный обход с лимитом глубины (2-3): найденные страницы → новые .onion → probe → пул. Dedup по onion-адресу. Rate limit на хост, чтобы не долбить.

**Критерий готовности:** с пустым `onion_pool` запускаешь discovery - через час пул содержит десятки живых категоризированных сервисов, поиск в deep mode работает без ручных сидов.

## Этап 3: Самосборный парсер (3-4 дня)

**Цель:** парсер строится по запросу под конкретный сайт, чинится сам.

### 3.1. Builder

`internal/parsers/builder.go`:
- `BuildParser(url, fields)` → снимает DOM (tls-client или rod, если антибот), выделяет структуру.
- Генерацию селекторов делает LLM-КЛИЕНТ через MCP: сервер отдаёт очищенный DOM-скелет (обрезанный `x/net/html` рендер), клиент возвращает mapping `field → selector`.
- Сохранение в `selectors` с confidence и стратегией.

### 3.2. Self-healing

Четыре стратегии по цепочке, дешёвые первыми:
1. Fuzzy class matching
2. Regex pattern matching
3. Structural context (родитель/сосед)
4. XPath fallback (`antchfx/htmlquery`)

Если все упали → регенерация через LLM-клиент (MCP-вызов с новым DOM). Confidence < 0.6 → триггер исцеления. Успешный парсинг повышает confidence.

### 3.3. Антибот-стек

Парсер знает про обход: если домен в списке защищённых (Cloudflare, DataDome) или ответ 403/капча → эскалация: tls-client с ротацией fingerprint → rod + stealth с прокси. Решение по факту ответа, не по конфигу.

**Критерий готовности:** `parse(url, ["title","price","email"])` на ранее неизвестном сайте → парсер собран, данные извлечены. После искусственной смены вёрстки парсер исцелился без ручного вмешательства.

## Этап 4: Классификация и каталог файлов (1-2 дня)

### 4.1. Классификатор источников

`internal/classifier/source.go`:
- Правила первыми (дёшево): наличие логин-формы, paywall-маркеры, капча, возраст домена.
- LLM-клиент - только для неоднозначных (сервер отдаёт сниппет, клиент судит).
- Выход: `{type: public|private|paid|scam, quality: 0..1, popularity: 0..1}`.

### 4.2. Каталог файлов (без скачивания)

`internal/catalog/files.go`:
- Найденные файлы НЕ качаются. Точка.
- Запись в каталог: url, filename, ext, size (из HEAD), mime, source_page, found_at, verdict.
- `verdict` по расширению: `safe-doc` (txt/csv/pdf/docx/xlsx), `archive` (zip/rar/7z), `executable-risk` (exe/scr/bat/ps1/vbs/js) - помечается, но не блокируется: решение о скачивании принимает человек на своей стороне.
- Дедуп по url.

**Критерий готовности:** после прогона поиска `file_catalog(task_id)` отдаёт структурированный список файлов с ссылками и вердиктами.

## Этап 5: MCP-сервер (3-4 дня)

**Цель:** весь функционал как MCP-инструменты, подключаемые к любому клиенту.

### 5.1. Транспорт

- `mark3labs/mcp-go`: stdio для локального, streamable-http для удалённого подключения.
- Авторизация по токену для http-транспорта.

### 5.2. Инструменты

| Tool | Назначение |
|---|---|
| `search` | query + mode(auto/fast/stealth/deep) + proxy_pool → результаты |
| `parse` | url + fields → структурированные данные (self-healing внутри) |
| `build_parser` | url + fields → собранный парсер, сохранён в реестр |
| `discover_onions` | запуск разведчика, отдаёт свежие живые источники |
| `classify_source` | url → тип/качество/популярность |
| `file_catalog` | task_id/query → каталог найденных файлов |
| `hunt_create` / `hunt_list` / `hunt_results` | фоновые мониторинги по ключевым словам |
| `pool_status` | состояние onion-пула и прокси-пула |

### 5.3. Подсказки клиенту

- MCP `prompts`: готовые системные подсказки для LLM-клиента (как выбирать режим, когда звать discover_onions, как читать вердикты каталога).
- MCP `resources`: pool_status, hunt-результаты как читаемые ресурсы.

### 5.4. Длинные задачи

Поиск/краул - фоновые горутины в реестре `tasks`, MCP отдаёт `task_id` + прогресс через notifications. Клиент не висит на таймауте.

**Критерий готовности:** Claude Desktop / любой MCP-клиент подключается к серверу и по фразе "найди утечки X" сам зовёт search → parse → file_catalog и возвращает отчёт.

## Этап 6: Охота, тесты, упаковка (3-4 дня)

- **Hunts:** периодический прогон запроса по расписанию, diff по hash выдачи, новые находки → событие/ресурс для клиента.
- **Тесты:** go test на поисковики (с httptest-моками), парсер (фикстуры-страницы), router, health-pool, proxypool (тесты уже есть в TeamSWAGbot - портировать).
- **Observability:** zerolog, метрики в SQLite (запросов/успехов/фейлов по модулям), tool `stats`.
- **Упаковка:** один статический бинарь (`CGO_ENABLED=0 go build`), `voidsearchswag setup` (скачивает Tor Expert Bundle, применяет миграции, проверяет окружение), весь стейт в `~/.voidsearchswag/`. Кросс-компиляция win/linux/darwin из одной команды.
- **Документация:** README (архитектура), docs/MCP.md (инструменты), docs/INTEGRATE.md (MCP-конфиг + импорт как Go-пакет).

**Критерий готовности:** чистая машина → скачал бинарь → `voidsearchswag setup && voidsearchswag run` → MCP-клиент из любого другого проекта подключается и работает.
