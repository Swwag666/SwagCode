# VoidSearchSwag

Умный поисковый движок как self-hosted MCP-сервер. Clearnet + Tor, самосборный парсер с self-healing, onion-разведчик, каталог найденных файлов. Мозг - любой MCP-клиент (Claude, свой агент), сервер - чистый инструментарий.

Один статический бинарь. Ноль внешних API и ключей. Стейт в `~/.voidsearchswag/`.

## Установка в один клик (Windows)

Кому лень руками: ветка `release` держит готовый бинарь, суммы и
установщик. `install.bat` сам проверит SHA256, поставит Tor, сгенерирует
токен и `start.bat` - Go не нужен:

```bat
git clone --depth 1 -b release <адрес-репо> vss
cd vss
install.bat
start.bat
```

Сервер поднимется на `127.0.0.1:3333`, токен - в `token.txt` (в argv не
светится). Подробности - README ветки `release`. Из исходников тот же
`install.bat` в корне main сам соберёт бинарь через `go build`.

## Быстрый старт

```bash
go run ./cmd/voidsearchswag setup     # весь стек: tor + база + chromium + проверка
go run ./cmd/voidsearchswag run       # MCP по stdio
go run ./cmd/voidsearchswag run --http 127.0.0.1:8800   # MCP по streamable-http локально

go run ./cmd/voidsearchswag search "golang context timeout"        # авто-режим
go run ./cmd/voidsearchswag search --mode deep "leak database"     # через onion
go run ./cmd/voidsearchswag onioncheck                             # живость onion-поисковиков
```

Подключение из Claude Desktop (`claude_desktop_config.json`) - готовый блок
печатает сам `setup` в конце, с абсолютным путём к бинарю:

```json
{
  "mcpServers": {
    "voidsearchswag": {
      "command": "C:/path/to/voidsearchswag.exe",
      "args": ["run"]
    }
  }
}
```

## Установка подробно

Нужен только бинарь: `go build` или готовый из релиза. Go, Docker, Python,
API-ключи не нужны. Весь стейт - в `~/.voidsearchswag/` (или `$VOIDSEARCH_DATA_DIR`).

```bash
voidsearchswag setup
```

Что ставит `setup`, по шагам:

| # | Шаг | Что происходит | Если упало |
|---|---|---|---|
| 1 | Tor Expert Bundle | скачивает с `dist.torproject.org` (зеркало через `VOIDSEARCH_TOR_DIST`), проверяет sha256, распаковывает в `vendor/tor/` | 503/геоблок - задай зеркало; `--no-verify` только если доверяешь источнику; `--offline` пропускает (бинарь уже лежит) |
| 2 | База | SQLite + миграции в `voidsearchswag.db` (WAL, `busy_timeout`) | почти нечему падать; проверь права на каталог |
| 3 | Chromium | rod докачивает браузер (~150МБ в `~/.rod`) и открывает пустую stealth-страницу | предупреждение, не ошибка: stealth деградирует на HTTP; свой бинарь - `VOIDSEARCH_CHROME_PATH`; пропуск - `--no-browser` |
| 4 | Прокси-пул | только с `--warm-pool`: тянет ProxyScrape, проверяет живость, кладёт state | предупреждение; добей вручную через `poolcheck` |
| 5 | Проверка tor | bootstrap до 100%, NEWNYM-ротация | `--skip-check` пропускает; без tor работают clearnet-режимы |

В конце `setup` печатает готовый JSON для MCP-клиента и команду первой проверки.
Дальше агенту доступны 27 инструментов (`docs/MCP.md`) и 8 промптов: разведка,
парсер, охота. Первая проверка живости onion-ядра: `onioncheck`.

Минимальный стек без сети и скачиваний: `setup --offline --no-browser --skip-check`
(нужны заранее положенные tor-бинарь и база). Обратное - всё и сразу:
`setup --warm-pool`.

## Команды

| Команда | Что делает |
|---|---|
| `setup` | весь стек: Tor Expert Bundle (sha256), миграции, chromium для stealth, bootstrap + NEWNYM, печать MCP-конфига. Флаги: `--offline`, `--no-verify`, `--skip-check`, `--no-browser`, `--warm-pool` |
| `run` | поднимает MCP-сервер и tor-демон |
| `search` | поиск из консоли: `--mode auto\|fast\|stealth\|deep`, `--limit`, `--no-cache`, `--json`, `--no-tor` |
| `onioncheck` | пинг onion-поисковиков: латентность, доля успехов, отключённые движки |
| `poolcheck` | прогрев прокси-пула ProxyScrape с проверкой живости |

## Поисковые режимы

Три режима, роутер выбирает сам или режим задаётся явно.

| Режим | Как работает | Когда |
|---|---|---|
| `fast` | DuckDuckGo HTML + Lite параллельно, без ключей | обычные запросы, поисковые операторы |
| `stealth` | то же + cloaked-браузер `rod` параллельно (DDG, при пустоте - Bing) | домены с антибот-защитой (avito, booking, cloudflare) |
| `deep` | ahmia-мост по clearnet + onion-поисковики через tor параллельно; при мёртвых движках - одна смена цепи (NEWNYM) и повтор | утечки, .onion, даркнет, paste |

Роутер считает режим по сигналам в запросе: `onion`/`leak`/`dump`/`combo`/`cve-` → deep, `avito`/`booking`/`captcha` → stealth, `site:`/`intitle:`/`filetype:` → fast, явных признаков нет → fast.

Если режим отдал пусто, включается цепочка фоллбэков (`FallbacksFor`): например `stealth → fast → deep`. В ответе видно `used_mode` и флаг `degraded` - то есть какой режим **реально** отработал, а не какой запросили. `deep` без живых onion-движков сам уходит на clearnet и помечает это в `report.note`.

Живой прогон stealth без кэша: `ddg-html:10 + rod-browser:4` за 14.5с - настоящий Chromium отрендерил DDG-выдачу и смешал её с HTTP-параллелью. Chromium rod докачивает сам при первом запуске (`~/.rod`), отдельный Playwright/Node не нужен.

Даркнет держится на двух опорах. Первая - ahmia-мост: clearnet-фронт `https://ahmia.fi` отдаёт onion-выдачу по прямому каналу без tor (с обязательным скрытым токеном формы - без него 302 на главную, токен читается с главной каждый раз, а не зашит). Вторая - onion-движки через tor с health-пулом; если все легли, ядро делает одну смену цепи (NEWNYM) и повторяет опрос, потому что чаще дохнет выходная нода, а не движки. Живой прогон через tor (`onioncheck`: tornet 4.3с, torch 15.4с, tor66/ahmia-onion мёртвы - health-пул их исключил): `search --mode deep` отдал 8 onion-результатов за 31с (`torch:16, tornet:7` - утечки баз, форумы, без флага `degraded`). Честная оговорка: backend clearnet-моста ahmia на момент проверки отдавал 504, поэтому мост помечается `fail` (с потолком 25с, deep не висит) и подхватит выдачу сам, как только backend оживёт. Без tor остаётся clearnet-фолбэк с пометкой `degraded`.

Зашитые сиды дохнут, пул растёт сам - deep чинится автопромоутом: живые сервисы проверяются на поисковую форму (формы входа отсекаются по password-полю, чужие action - по хосту), кандидаты гоняют пробный запрос, прошедшие порог onion-ссылок поднимаются в каталог и health-пул сразу, сид пишется в таблицу `engines`. Консоль: `promote`, инструмент: `promote_engines`, фон: каждый цикл разведки (`VOIDSEARCH_PROMOTE_LIMIT` проверок). Код возврата `promote`: ноль - движки подняты, либо проверки состоялись и просто не дали кандидатов, либо проверять было нечего; единица - ни одна проверка не состоялась (tor мёртв, адреса недоступны) или найденный сид не удалось сохранить. Обвязка в cron читает код, а не текст отчёта, поэтому «проверено 9, поднято 0, отказов 9» больше не выглядит успехом. Частичный успех - хотя бы один поднятый движок при отказах остальных - остаётся нулём: регулярный прогон обязан реагировать на «ничего не сделано», а не на «пул не идеален».

Выдача ранжируется по релевантности запросу: пересечение токенов с заголовком (×3) и сниппетом/урлом, бонус onion в deep, штраф безымянным и монополии движка. Сортировка стабильная, ранги переназначаются. Счётчики всего - в `metrics` и на `GET /metrics` (за тем же Bearer).

## Архитектура

```
cmd/voidsearchswag   точка входа (setup/run/search/discover/collect/files/poolcheck)
internal/netx        сетевой стек: прокси-пул, fingerprint (TLS JA3/JA4), tor-ротатор
internal/httpc       антидетект-транспорт: tls-client + impersonate, ручная распаковка, классификация блокировок
internal/searchers   движки: DuckDuckGo, cloaked-браузер rod (DDG+Bing), ahmia-мост, onion-каталог, health-пул
internal/search      ядро: маршрутизация, цепочки фоллбэков, кэш
internal/router       выбор режима по сигналам запроса
internal/store       SQLite (modernc, без CGO) + миграции
internal/config      конфиг из env (VOIDSEARCH_*)
internal/setup       установка Tor Expert Bundle
internal/mcpserver   MCP-инструменты и промпты (mark3labs/mcp-go)
internal/discover    onion-разведка: каталоги, рекурсивный обход, пул, пробы живости
internal/catalog     сбор файлов: обход страниц сервиса, замер размеров, запись в каталог
internal/filex       разбор ссылок на файлы: расширения, Content-Disposition
```

Полный справочник всех 62 `VOIDSEARCH_*`-переменных - в [docs/env.md](docs/env.md); тест `TestEnvReferenceCoversAllConfigVars` не даёт справочнику разъехаться с кодом.

Портированный боевой стек из TeamSWAGbot: прокси-пул с самоотсевом (dead/banned/suspect, персистентный state, LRU), 7 TLS-отпечатков браузеров, tor NEWNYM-ротация.

### Транспорт и антидетект

`internal/httpc` держит пару клиентов на одном отпечатке: `bogdanfinn/tls-client` (TLS + HTTP/2 через uTLS) и `impersonate-http` (байт-в-байт ClientHello + порядок заголовков). Сессия переиспользуется до `SessionTTL` или пока rotator жив.

Сжатие распаковывается вручную (gzip, zstd, brotli, deflate - и zlib, и raw), потому что `Accept-Encoding: gzip, deflate, br, zstd` обязателен для отпечатка Chrome, а авто-декомпрессия на h2 и h1 у tls-client ведёт себя по-разному. Сначала используется явный `Content-Encoding`, магия байтов - только как запасной путь.

Блокировки классифицируются: `BlockIPBan`, `BlockEdge`, `BlockRate`, `BlockAuth`, `BlockCaptcha`. На 403/429/451 прокси помечается suspect в персистентном пуле. При блокировке включается `Escalate` - ротация идентичности и повтор через второй транспорт.

### Жизненный цикл tor

Tor-демон запускается с `--__OwningControllerProcess <pid>`, поэтому умирает вместе с приложением даже при `kill -9`. Без этого флаг orphan-процесс держал `tor-data/lock` и следующий запуск не мог подняться. Проверено на tor 0.4.9: ~1-4 сек после смерти родителя. Отключается `VOIDSEARCH_TOR_OWN_PROCESS=false`.

`Healthy()` делает живой пинг control-порта (`GetInfo("version")`, таймаут 3с), а не проверку указателей.

### Onion-пул

Половина onion-поисковиков мертва в любой момент, поэтому живость отслеживается: `HealthPool` пингует каждый движок, считает скользящую латентность и долю успехов, после 3 провалов подряд отключает до восстановления. `searchDeep` берёт только живые, а если живых нет - пробует все.

Движки опрашиваются **одновременно**, а не по очереди: последовательный обход с ранним выходом по лимиту оставлял остальные неопрошенными, как только первый отдавал достаточно результатов. Когда набрано вдвое больше лимита, отстающим даётся окно дозора (`engineGracePeriod`, 20с) - иначе один зависший поисковик держит всю выдачу до своего таймаута.

На каждый движок нужен **свой** параметр запроса: torch понимает `/search?query=`, tornet и tor66 - `/search?q=`, ahmia - `/search/?q=`. С неверным параметром движок молча отдаёт главную страницу, и это выглядит как рабочий поиск. Сиды заданы с проверенными путями и селекторами.

Ссылки самого движка (навигация, `/about`, `/serviceinfo`, self-ссылки) отсеиваются: без этого движок, чей селектор не сработал, отдаёт свою навигацию как результаты поиска.

Tor ждёт готовности цепей. `StartTorDaemon` возвращает управление, как только открылись socks- и control-порты, а это происходит задолго до готовности: порт слушает, но любой запрос через него до bootstrap 100% падает по таймауту. Поэтому после подключения control-порта `waitBootstrap` опрашивает `status/bootstrap-phase` до `PROGRESS=100` (обычно ~25-30с).

Текущие живые движки: torch, tornet, tor66. Ahmia отвечает, но отдаёт страницу-заглушку. Сиды переопределяются через `VOIDSEARCH_ONION_ENGINES` в формате `имя|url|путь|селектор|категория`, несколько через запятую.

## Onion-разведка

`internal/discover` собирает onion-адреса из публичных каталогов и обходит найденные сервисы. Clearnet-источники (ahmia.fi, dark.fail, onion.live, tor.watch) опрашиваются одновременно и не тратят tor-канал; падение одного не роняет остальные, отчёт по каждому независим.

**Валидация адресов строгая.** Onion-адрес - base32-строка длиной 16 (v2) или 56 (v3) по алфавиту `a-z2-7`; цифры 0, 1, 8, 9 в base32 не существуют. Голые адреса в тексте, ссылки со схемой и мусор вида `aaa111bbb222cccc.onion` проходят одну проверку - без неё мусор уходит в пул и жжёт tor-цепочку впустую.

**Рекурсивный обход** идёт слоями по глубине, каждый хост обходится ровно один раз: повторный заход бессмыслен и заметен для сервиса. Между запросами к одному хосту держится пауза (`VOIDSEARCH_DISCOVER_DELAY`, 2с) - без неё обход забивает onion-сервис и получает бан вместо данных. Потолок хостов и глубины отражён в отчёте полем `limit_hit`, а не молча обрезает выдачу.

Дедупликация - по onion-адресу: один сервис попадает в пул один раз, сколько бы источников его ни отдали. Повторный прогон идемпотентен: известные адреса не считаются новыми, а `sources` не растёт. Найденное пишется в `onion_pool`, откуда адреса берут поиск и пробы живости.

Живой прогон: `discover --depth 0` собрал 10130 адресов из 7 источников за ~7с (ahmia-каталог дал 10029, dark.fail 32, onion.live 15, tor.watch 67, hidden-wiki 79, tor.link 39). Повторный прогон даёт новых 0.

## Пробы живости

`internal/discover/probe.go` прогоняет волну проб по пулу через tor. Проба - это только факт ответа: тело не читается, важны статус и время.

Латентность сглаживается (`(avg*3 + new)/4`), доля успехов и серия провалов обновляются накопительно: одна случайная неудача не выбрасывает живой сервис из пула, один удачный ответ не возвращает мёртвый. Три провала подряд помечают сервис мёртвым, первый же успех сбрасывает серию.

Параллелизм держится умеренным (8 по умолчанию): слишком много одновременных цепей через один tor-демон даёт таймауты у всех сразу. Порядок результата детерминирован - адреса сортируются до обхода.

Живой прогон: `probe --limit 12` - живых 11 из 12 за 1м8с, латентность от 3.4с до 39с.

Код возврата `probe`: ноль - хотя бы один запрос ушёл в сеть либо проверять было нечего; единица - все пробы пропущены, потому что нет ни tor, ни прокси. Строка «живых 0 из 7 (пропущено 7: нужен tor или прокси)» означает, что состояние пула неизвестно, а не что сервисы мертвы, и обвязка в cron обязана видеть это по коду, а не по чтению отчёта. Отказ отдельного адреса провалом не считается: диагностика затем и запускается, чтобы находить мёртвые, поэтому «все опрошенные молчат» остаётся нулём.

`onioncheck` берёт живость из health-пула, то есть из прошлых волн, поэтому при пропущенных проверках строка называет источник: «живых 3 из 7 по прошлым замерам (пропущено 7: нужен tor или прокси)», а над таблицей добавляется «состояние ниже - по прошлым замерам, в этой волне не проверялось». Без оговорки тот же прогон выглядел как «живых 3 из 7 (пропущено 7)» и утверждал текущее состояние пула, которого команда не проверяла, а таблица показывала «tornet жив, успех 93%, проб 29» - числа из истории при нуле проб в этой волне. На свежей базе ноль живых означает отсутствие истории, а не смерть движков. Когда волна состоялась, оговорок нет: «живых 3 из 7», а при частичном пропуске строка добавляет «живость непроверенных по прошлым замерам». Код возврата у `onioncheck` тот же, что у `probe`: ноль - хотя бы один движок спрошен либо проверять нечего, единица - вся волна пропущена. Мёртвые движки при состоявшемся пинге остаются нулём, потому что диагностика затем и запускается, чтобы их находить, а «живых 0 из 7» после настоящей волны - это результат, а не сбой команды.

## Каталог файлов

`file_catalog` хранит найденные файлы: URL, имя, расширение, размер, MIME, страница-источник, вердикт. Поиск (`SearchFiles`) идёт по подстроке в имени или URL, расширению, диапазону размера и задаче; сортировка - по размеру убыв. Символы `%` и `_` экранируются, поэтому запрос с ними ищет буквальное совпадение, а не произвольный шаблон.

Каталог наполняется двумя путями. Первый - обход разведки: страница уже скачана, поэтому файловые ссылки вытаскиваются из неё тем же проходом, без второго захода по адресам. Второй - команда `collect`: она целевым образом обходит живые хосты пула, спускается по внутренним страницам (главная почти всегда отдаёт только разметку) и умеет распознавать выдачи без расширения в адресе - по `Content-Disposition`.

Что попадает в каталог: архивы, документы, дампы, ключи, образы, медиа. Что не попадает: `css`, `js`, `html`, картинки, шрифты - разметка сервиса содержимым не является. Уникальность записи по `url`: один файл, найденный в разных прогонах, это одна строка с уточнённой метой. Пустые значения при повторной записи не затирают уже известные - размер, однажды замеренный, сохраняется.

Размер берётся только по заголовку `Content-Length`, тело не читается. Замер идёт параллельно и ограничен по числу файлов за прогон: это отдельный запрос на файл, и на большом обходе он может занять больше времени, чем сам обход.

Ошибка прошлых версий, найденная на живой базе: обход писал в каталог картинки и стили. Путь вида `/wp-content/uploads/` намекает на скачивание, но расширение при этом картиночное - в каталоге оказались 184 `jpg` и 61 `png` вместо файлов содержимого. Теперь в каталог идут только известные файловые расширения, а мусорные строки вычищаются разовым проходом при каждом сборе.

Консоль: `collect --limit N` собирает с живых хостов, `files --query/--ext/--min-size/--task` ищет по каталогу. `--query` ищет подстроку в имени файла, в его адресе и в адресе страницы, на которой он найден: имена в собранных каталогах машинные, и страница часто единственный осмысленный признак группы. `--ext` и `--verdict` - списки: значения разделяются запятой, пробелом или точкой с запятой, и флаг можно повторять, поэтому `files --ext pdf --ext epub` равно `files --ext pdf,epub`. Раньше повтор молча перезаписывал прежнее значение: на каталоге из 19 файлов (epub 6, mp4 11, pdf 2) команда `files --ext pdf --ext epub` возвращала 6 записей вместо 8, а `files --verdict ebook --verdict document` - 2 вместо 8, и ни одна строка вывода не намекала на потерю фильтра.

Метка категории приводится к нижнему регистру при записи: `AddFile` нормализует `verdict` правилом `filex.NormalizeVerdict`, тем же, которым пользуются проверка риска и объяснение метки словами. До правки правило знали два места из трёх, и запись с меткой `EXECUTABLE` распознавалась как риск, но объяснение уходило в общее «файл требует осторожности» вместо «исполняемый код, запускать только понимая происхождение файла», а `files -verdict executable` её не находил: фильтр сравнивает нормализованный ввод с колонкой точно, чтобы оставаться на индексе `idx_file_verdict`, и пустой ответ был неотличим от «таких файлов нет».

## Поиск по пулу

`SearchOnions` ищет по собранной базе сервисов: заголовок, описание, адрес. Мёртвые записи по умолчанию исключены: сервис, который не отвечает, в выдаче - мусор.

Заголовок берётся только из текста самой ссылки в каталоге. Подпись вида «Название http://адрес.onion» урезается до названия, а подпись, равная адресу, отбрасывается совсем: заголовок-адрес хуже отсутствующего, потому что по нему нельзя искать, а вид он делает. Обрывки разметки (`/"`, `href="/x`), замеры времени в начале строки (`4.0s ...`) и HTML-сущности (`&#039;`) вычищаются.

Ошибка прошлых версий, найденная на живой базе: подпись приписывалась соседнему адресу - у `recon222…` стояло название от `drughub…`. Из 10138 «заголовков» 10081 оказались самим адресом, а 57 - чужими. Теперь сбор берёт мету только из ссылки, а не из текста рядом, и разово вычищает уже записанный мусор.

Живой прогон: 10135 адресов, из них 7 с настоящими названиями (AirVPN, HostMeNow, Deep Search и др.).

## Самосборный парсер

`internal/parser` строится по запросу под конкретный сайт. `build_parser` отдаёт DOM-скелет (тег, id, классы, текст ключевых узлов; `script/style` вырезаны), LLM-клиент возвращает mapping через `save_selector`, селекторы лежат в таблице `selectors` с ключом по хосту.

Self-healing идёт по цепочке, дешёвые первыми: точный CSS (1.0) → XPath (1.0, переживает переименование классов) → fuzzy-класс `[class*="токен"]` (0.8) → regex `поле: значение` (0.6) → structural/mailto/атрибуты и generic `title/h1/meta` (0.5). `healed=true` в ответе `parse` значит: значение взято запасной стратегией, селектор надо перегенерировать. Успешный точный разбор поднимает confidence обратно до 1.0. Отдельный случай - недоступна сама база селекторов: разбор уходит в те же запасные стратегии, но селекторы в порядке, и совет перегенерировать их увёл бы от причины. Тогда ответ несёт `warning`: поле в JSON и строка `внимание:` в текстовом режиме, напечатанная раньше совета о селекторах. Замер на сохранённом `.price-tag`: на открытой базе `strategy=css confidence=1.0 healed=false`, на закрытой - `strategy=structural confidence=0.5 healed=true` плюс `warning` с причиной.

Консоль: `parse --fields title,price <url>`. Флаг `--fields` можно повторять: `--fields title --fields price` равно `--fields title,price`, значения накапливаются. До правки повтор перезаписывал предыдущий список, и `parse --fields title --fields description https://example.com/` разбирал только description: поле терялось, а код возврата падал в 1 с «ни одно поле не извлечено».

## Классификатор и охота

`internal/classifier` считает по правилам, без сети: форма входа (`type=password` + второй маркер) → `private`, paywall-подписка → `paid`, деньги + гарантия/удвоение → `scam`, остальное → `public` с урезанием качества до 0.3 при капче. Каждый вердикт сопровождается `reason` — видно, какое правило сработало. Консоль: `classify <url>`.

`internal/hunt` гоняет мониторинги по расписанию (`schedule_min`, дефолт 360): hash выдачи считается по отсортированным URL без дублей, первый прогон фиксирует базу и находкой не считается, смена hash — находка. Находки дублируются push-уведомлением `notifications/hunt_update`, ожидание без поллинга — `hunt_watch`/`hunt watch`. Консоль: `hunt create|list|run|watch`, сводка — `stats`.

## Фоновая жизнь сервера

`run` не витрина статичной базы: циклы работают сами. Охота (`VOIDSEARCH_HUNT_BG`, каждые `VOIDSEARCH_HUNT_INTERVAL`) прогоняет due-запросы и пушит находки клиентам уведомлением. Разведка (`VOIDSEARCH_DISCOVER_BG`, каждые `VOIDSEARCH_DISCOVER_BG_INTERVAL`) собирает адреса из каталогов с обходом, проверяет живость в пределах `VOIDSEARCH_DISCOVER_BG_PROBE` проб и поднимает найденные поисковики в каталог. Бэкап (`VOIDSEARCH_BACKUP_BG`, каждые `VOIDSEARCH_BACKUP_INTERVAL`) снимает базу онлайн (`VACUUM INTO`) в `VOIDSEARCH_BACKUP_DIR`, держит `VOIDSEARCH_BACKUP_KEEP` штук. Интервалы клампятся снизу (1м / 1ч), остановка - Ctrl+C вместе с сервером. Статистика здоровья движков переживает рестарт: пишется в таблицу `engine_health` и подтягивается на старте.

HTTP для чужих сетей: не-петлевой адрес без токена не поднимается вовсе - запуск отклоняется до открытия базы и предлагает три выхода (`--token`/`--token-file`, адрес `127.0.0.1` либо явный `--http-allow-open` для изолированного стенда). `--tls-cert` + `--tls-key` включают TLS напрямую, токен лучше класть в файл (`--token-file`, env `VOIDSEARCH_HTTP_TOKEN_FILE`, права 0600) - `--token` светится в `ps`. Метрики - `GET /metrics` за тем же Bearer. Демон: `docs/voidsearchswag.service` (systemd), `docs/windows-service.md` (sc.exe / NSSM). Конфиг файлом: `docs/config.example.json`.

## Судья и кластер

LLM-судья учит реранк: промпт `judge` ведёт агента по цепочке search → оценка 0..1 → `judge_submit`. Голоса копятся в таблице `relevance`, ночной тик считает бонусы хостов (среднее с весом 1/sqrt(голосов автора), порог 3 голоса, кламп ±3 = вес токена в заголовке). Голос привязан к запросу: бонус, вес автора и порог доверия считаются в пределах того же запроса, поэтому оценка выдачи про утечки не переставляет результаты запроса про рецепты. Холодный старт ничего не меняет: без голосов реранк базовый.

Локальный кластер - реплики с gossip-синком (`docs/CLUSTER.md`, скрипты `docs/cluster-local.sh/.bat`): три полных инстанса, общий токен, `peer_sync` мержит пулы и охоты с дедупом, фон синкается каждый час. Падение ноды - переподключение агента, находки дедупятся по `hunt_id + hash`.

Живой прогон (direct, без tor): `search --mode fast` отдал 5 результатов за 1.8с (`ddg-html:10`, `ddg-lite:fail` - честно в отчёте); `parse` вытащил `title=Example Domain` через generic с `healed=true`; `hunt run --id` зафиксировал базу из 18 URL, повтор - `changed=false`, плановый `hunt run` - `пропущено 1` по расписанию.

Текстовый вывод объясняет каждый отказ: под строкой «движки:» причина печатается по движкам - недоступный без tor onion-адрес, таймаут, нераспознанная разметка, пустой ответ. Поэтому `ahmia:fail` больше не требует запуска с `--json`, чтобы узнать, что именно случилось, а лечится каждый отказ по-своему. Причина усекается до 160 символов, чтобы длинный onion-адрес не ломал выравнивание, пустая отмечается как «без описания», а в выдаче из кэша строка движков помечена как запись кэша: она описывает прошлый прогон, а не текущий.

## Хранилище
